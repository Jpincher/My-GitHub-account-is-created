Download all three ZIPs, the recovery HTML manual and the private Word guide. Save a second copy on a separate disk. Extract each ZIP separately, preserving folders. Each archive is a source/media snapshot, not a full Git history backup.

## 6. View on your own computer

Install Python 3 if it is not present. On macOS open Terminal; on Windows open PowerShell or Terminal. Change to the chosen extracted Website folder, for example: cd followed by a space, then drag that folder into Terminal and press Return.

macOS/Linux: python3 -m http.server 8000 --bind 127.0.0.1 . Windows: py -m http.server 8000 --bind 127.0.0.1 . Leave that window open and visit http://127.0.0.1:8000/ in Safari or another browser.

Use the homepage package to see the portfolio, or the learning package to see the learning entry. To show the complete combined backup start at /index.html, then /interactive-learning.html. Press Control-C in the terminal to stop the server.

Serve only Website/, never the parent folder holding private guides or data exports. No Node, build step or speech-provider account is needed to play the installed recordings and view the static website.

Double-clicking HTML with a file:// address may display simple pages, but is not the reliable test method: navigation, browser storage, popup messaging and live forms work differently. Use the local HTTP server for rebuilding and testing.

## 7. Share on a LAN or another web server

For a trusted LAN demonstration, start the server from Website using python3 -m http.server 8000 --bind 0.0.0.0 (or py on Windows). Find the host computer’s private IP address in its network settings. On another device connected to the same LAN open http://HOST-PRIVATE-IP:8000/ , for example http://192.168.1.25:8000/ . Do not use 127.0.0.1 on the second device; it points at that device.

Allow the chosen port through the host firewall only for the trusted local network. Guest Wi-Fi, client isolation or school network restrictions may block peer access. Stop the server when the demonstration finishes; keep the host awake.

Python http.server is suitable for temporary local viewing. For an ongoing LAN service use an administered static web server such as nginx, Apache or IIS with Website as its document root. For a public host use HTTPS and the host’s managed publishing process. Copy the Website contents to public_html, wwwroot or the configured document root, not the ZIP or its outer archive folder.

The static site does not run Python or a database on GitHub Pages. The Python command only serves existing files locally. A full local feedback database is a separate deployment; copying static files to a LAN server does not install Supabase or send email.

HTTP LAN addresses may not provide the secure browser features needed for protected login. Use HTTPS for ongoing LAN feedback collection and configure the API’s allowed origin. Temporary static demonstrations can still show the learning material and installed media.

Automatic shared feedback collection is separate from the static site. Keeping the existing Supabase project alive allows the restored original site to use existing responses immediately; no database rebuild is needed for a routine HTML restore.

Export responses now: open the current online tester with #developer, enter your developer code, use the detailed export button and save its JSON privately. The developer JSON export is a portable feedback dataset, not a full database backup and not an automatic website import file. No import screen is provided. To resume that dataset in another database, use the documented trusted restore tool described below; never upload personal data to GitHub.

For a complete operational database backup, sign into Supabase and use its current database backup/CLI guidance. Preserve schema and response/outbox data privately. PostgreSQL backups do not automatically back up Edge Function source or account settings; those source files are included here. Avoid carrying active owner sessions, rate-limit rows or old notification tokens to a new deployment.

Backend source: supabase/schema/usability-live.sql creates tables, private grants/policies and functions. supabase/schema/usability-notification-cron.sql installs five-minute retry scheduling. supabase/functions/usability-api/index.ts implements the API; core.mjs validates scores and creates anonymous email summaries; deno.json configures the function.

To rebuild from zero, use a NEW empty Supabase project, retain a private backup of any existing project, and apply usability-live.sql once through its SQL editor. Do not reapply the fresh-install schema over live tables or delete real responses to make the script run.

Set the owner email and allowed site origin in index.ts for the intended deployment. Keep service secrets server-side. Deploy usability-api with JWT gateway verification disabled because this function handles public collection and server-verified owner login itself. Keep its private record checks intact.

Using the current Supabase CLI, inspect supabase --help and supabase functions deploy --help. After login and linking the correct project, deploy usability-api from its source folder and set its configured entrypoint to index.ts. The included recovery/config.toml.example records verify_jwt=false and the entrypoint; do not overwrite an existing project config without reviewing it.

First owner login initializes jp_usability_live_config with that project’s API URL and a newly generated notification token. Use the recovery service console to sign in and send a clearly labelled, non-recording setup email. Activate FormSubmit from the owner inbox if asked, then verify receipt, individual scores and running totals.

Only after actual inbox verification, set delivery_verified=true for id=true through trusted Supabase SQL tooling. Use the recovery service console to Enable collection. Install the notification-cron SQL after checking pg_net and pg_cron extensions and avoiding duplicate cron jobs.

Set the frontend endpoint in usability-live-config.json AND the embedded window.JP_USABILITY_LIVE object in usability-tester.html. The live form uses the embedded object, not a runtime fetch of the JSON file. Updating the JSON alone will not reconnect an already-converted form. Keep tools/usability-live-client.js and enable-live-usability.cjs consistent if regenerating it.

For a changed hostname, update index.ts ORIGIN to the exact scheme + host + optional port; update its FormSubmit Referer to the actual tester URL, and update core.mjs’s Private response report URL, then redeploy. The current function permits one origin. Same-host different repository paths share an origin; a localhost port or LAN IP is a different origin. Do not change the production backend just to authorize an untrusted preview.

Verify health returns ready=true and deliveryVerified=true, anonymous records requests are rejected, public averages contain no personal fields, owner login works, grants/RLS remain private and the retry job is active. The supplied no-write smoke test checks the existing deployment; change its config and expected origin before testing a new host.

Use Developer only to check detailed responses and exports; owner sessions expire after 45 minutes and Lock clears them. ## 10. Restore an exported feedback dataset

The included recovery/restore-feedback.mjs reads a Developer-only JSON export and writes response rows directly through the trusted backend REST API using a server secret supplied in your local environment. It is an owner tool, not browser code. It does not create emails or notification-outbox entries, and it does not reset existing feedback.

Use only on a new/restored backend after installing its schema. First run node recovery/restore-feedback.mjs PATH-TO-PRIVATE-EXPORT.json with SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY set privately in your terminal environment. Its default mode validates and reports counts without writing. Run the same command with --apply only after reviewing the destination and counts.

Do not paste secret values into public code or this guide. Use your password manager and a private terminal session; close it when finished. The restore tool validates the live export format, preserves response IDs and timestamps, skips identical records already present, and refuses conflicting records. It inserts only new responses and never deletes or overwrites records.

Run with the matching backend version so ratings/profile validation remains correct. It restores accumulated responses so aggregate SQL can calculate public means. Notification history must be preserved from an operational database backup if that is required; historical responses imported by this tool deliberately generate no new notification emails.
